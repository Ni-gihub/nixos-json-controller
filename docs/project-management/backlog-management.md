# プロジェクトとバックログの運用

この文書はNXCの作業をどの単位で計画・追跡するかを定める。Issue本文の書き方は[Issue の書き方](./issue-writing.md)を正とする。

## 正本となるIssue

- **Project / プロジェクト憲章:** [#166 — NXC：安全で再現可能な NixOS パッケージ管理と App Store](https://github.com/nxc-project/nixos-json-controller/issues/166)
- **PBL / Product Backlog List:** [#167 — NXC Product Backlog](https://github.com/nxc-project/nixos-json-controller/issues/167)

#166はプロダクト全体の目的、スコープ、成功基準、リリースゲートを定義する。#167は現在のPBI、優先順位、依存関係、完了・見送り履歴への索引である。PBLは作業の詳細を重複保管せず、個々のIssueを参照する。

## 作業の階層

```text
Project (#166): プロダクト全体の目的・スコープ・成功基準（憲章）

PBL (#167): PBIを列挙する優先順位付き索引（親Issueではない）

PBI: 1つのユーザー価値を管理する親Issue
├── Task: PBIの成果に寄与する独立した作業
├── Bug: そのPBIの達成を妨げる不具合
└── Spike: そのPBIに必要な調査・技術検証
```

親子関係としてGitHubのSub-issuesに登録するのは、PBIと、その成果を実現するTask / Bug / Spikeの組み合わせである。Project #166とPBL #167は目的・索引の役割を持ち、すべてのPBIをぶら下げる親Issueにはしない。PBLはPBIへのリンク、優先順位、状態、依存関係、完了・見送り履歴を保つ。

新規のTask / Bug / SpikeをPBIの子にする場合は各フォームの `Parent PBI number (optional)` に親PBI番号を入力する。Owner / Member / Collaboratorが作成したIssueでは、GitHub Actionsが親がType `PBI`、子がType `Task` / `Bug` / `Spike` であることを確認してSub-issues関係を設定する。外部ユーザーが作成したIssueは自動変更せず、メンテナーがレビュー後に親PBIのSub-issuesから追加する。既存Issueは親PBIのページで **Sub-issues → Add existing issue** を使って紐づける。本文中の番号リンクやPBLの一覧だけでは、ネイティブな親子関係が設定済みとはみなさない。

## PBI・Task・Bugの使い分け

### PBI
利用者・運用者が得る成果に名前を付ける。例えば「カタログでインストール可能なアプリを識別できる」のように、価値が読み取れる単位にする。機能の全実装ステップをPBIの名にしない。

### Task
PBIを実現する独立した作業や調査を追う。例えばGUIの本番配布PBIに対し、CSP監査・ライセンス整理・Nix package実装などは異なる判断・成果を持つ作業として個別Issueで扱える。Taskの成果には対象PBIへのリンクを付ける。

### Bug
不具合の現象と期待値を追う。バグの原因が分かった後も、Bug本文は観察事実を保持し、修正の詳細やテスト結果は関連PRに記録する。

### Project / PBL
作業Issueの代わりにはしない。憲章は実装Taskを直接背負わず、PBLは同じAcceptance Criteriaを複製しない。作業中Issueだけではプロダクト全体の成功を測れないため、PBIの成果で評価する。

## 優先順位

優先度はPBL上で管理し、Issueのタイトルやラベルに順位を埋め込まない。初期判断は次の通り。

- **P0 — Release blocker:** セキュリティ、ライセンス、公開・配布の可否に直結する。通常機能より先に解消する。
- **P1 — Core outcome / correctness:** 安全性、正確性、主要機能の成立、利用不能・誤操作につながる不具合など、主要な成果や利用フローを阻害する。
- **P2 — Core UX / product capability:** 主要な利用フローを完成させる機能、待ち時間や不要な再処理を減らす改善など、日常利用の流れを直接改善する。例：詳細画面から一覧へ戻った際に検索結果を再利用する #172。
- **P3 — UX polish:** 主要な利用フローを大きく阻害しない、限定的な表示不具合・見た目・操作感の磨き込み。安全性や主要操作の正確性に影響する場合はP1以上へ引き上げる。

優先度とIssueの状態は別物である。優先度は順番、Statusは現在の作業状態、GitHubのopen/closedはIssueの受付状態を表す。クローズ済みであっても歴史的記録はPBLに残すが、見送りを完了実績として集計しない。

## 依存関係・重複の扱い

- ブロッカーがある場合は、PBLとIssue本文に「Blocked by #番号」「Blocks #番号」と書く。
- 関連するが順序に影響しないIssueは「Related: #番号」とする。
- 同じ成果を扱う重複Issueを作らない。新しい再現事実・スコープがある場合は、旧Issueをむやみに再オープンせず、新しいIssueから履歴を参照する。
- PRは関連Issueを明示する。Issue全体の完了ではないPRに `Closes #番号` を安易に使わない。
- PBIが大きすぎる場合は、ユーザー価値の異なる複数PBIに分割し、同じ価値を達成する技術作業はTaskへ分解する。
- 受け入れ条件や技術方針を変更した場合は、PBLの短い要約とIssueリンクを同期し、同じ長文を二重管理しない。

## 状態の意味

GitHubのIssue open/closedだけで進捗を表現しない。コメント、PR、Project boardを利用する場合は、少なくとも次の意味を共有する。

| 状態 | 意味 |
| --- | --- |
| 未整理 | 背景・重複・優先度を確認中 |
| 着手可能 | 問題と完了判断が理解でき、作業や調査を始められる |
| 作業中 | 実装・調査を進めている |
| レビュー中 | 対応PRのレビューを依頼している |
| 完了 | 成果を確認し、受け入れ条件を満たした |
| 見送り | 今回は対応しないと判断した |

これは推奨状態の定義であり、ネイティブProject boardのフィールドや自動化を実際に設定したという意味ではない。Project boardを設定する場合は、Type・Status・Priorityを別フィールドとし、既存Issueの一括登録や既定値も確認してから運用を始める。

## PBLの更新ルール

PBL #167 は初期スナップショットから始め、次のときに更新する。

- 新規PBIを追加または既存PBIの優先度を変更したとき
- Issueの状態・終了理由が変わったとき
- 依存関係が変わったとき
- 完了済み項目や見送り判断を別カテゴリへ整理したとき

PBLの集計には、対象期間・取得日・状態の内訳を記載する。Issue件数だけでなく、優先順位の理由と残るリスクを読めるようにする。PBL本文の状態集計は作成時点のスナップショットであり、GitHubの最新状態を自動集計していると誤解させない。

## PRの完了報告

PR説明では、必要に応じて次を記載する。

- Why：何の問題をどう変えるか
- 実装内容：主要な責務・動作の差分
- 受け入れ条件：関連PBI / Bugの条件に対応する確認
- 検証：実行したコマンド、確認手順、実際の結果
- リスク：互換性、安全性、性能、rollback、未確認事項

詳細ログや全テストケースをPR本文へ貼り付けず、CIや関連コメントへリンクする。確認していないテストを成功扱いにしない。
