# Issue の書き方

この文書を、NXC の Issue を作成・レビューする際の共通ルールとする。GitHub Issue Form は入力を助ける入口であり、本文の責務・粒度・判断基準はこの文書を正とする。

関連文書:
- [Backlog / プロジェクト構成](./backlog-management.md)
- [プロジェクト憲章 #166](https://github.com/Ni-gihub/nixos-json-controller/issues/166)
- [Product Backlog #167](https://github.com/Ni-gihub/nixos-json-controller/issues/167)

## 基本方針：Why から始める

Issue は、担当者が問題と期待する結果を理解し、必要な調査・設計・実装・レビューへ進める入口である。最初から完成した仕様書にすることを目的にしない。

起票時に優先するのは次の3点。

1. **誰が、どの場面で困っているか。**
2. **現状はどうなっていて、どんな影響があるか。**
3. **何ができる／どうなれば改善と判断できるか。**

解決方法・内部構造・詳細なテストケースが未確定でも、分かっている事実から起票してよい。分からないことを推測で埋めず、「未確認」「仮説」と明示する。Issue のタイトルを本文に重ねて書かない。

## Issue の種類

NXC は個人所有リポジトリでも利用できるよう、タイトル接頭辞で作業の種類を明示する。領域ラベル（`gui`、`safety`、`performance`、`packaging`、`testing` など）は担当領域を表し、Issue の種類とは区別する。

| 種類 | タイトル | 目的 | 本文の中心 |
| --- | --- | --- | --- |
| プロジェクト | `[PROJECT] ...` | プロダクト全体または大きな取り組みの目的・スコープ・成果を定義する | 背景、目的、対象範囲、成功基準、リリースゲート |
| PBL | `[PBL] ...` | 優先順位付きバックログと履歴の索引を維持する | PBIへのリンク、優先度、状態、依存関係、完了／見送り履歴 |
| PBI | `[PBI] ...` | 利用者や運用者に提供する価値・体験を管理する | ユーザーストーリー、Why、観察可能な成果、受け入れ条件 |
| Task | `[TASK] ...` | PBIの成果に寄与する、独立して実行・レビューできる作業を管理する | なぜ必要か、対象・方針、作業完了条件、検証 |
| Bug | `[BUG] ...` | 現在の動作と期待する動作の差を修正する | 実際の挙動、期待する挙動、再現条件、影響、修正後の確認 |
| 相談・調査 | `[相談]` / `[SPIKE]` | 方針・原因・実現可能性など、まだ決定していないことを明らかにする | 何を決めたいか、既知の事実、調査範囲、成果物 |

タイトルは何を解決するか、またはどういう結果を得るかを具体的に書く。「UI改善」「調査する」「対応する」のような目的が読み取れない表現だけにしない。既存Issueの接頭辞を変更する場合は、PBL側のリンクと検索性を確認する。

## PBI：ユーザー価値を書く

PBIは、原則として1つのユーザー価値・成果にまとめる。作業数・変更ファイル数・PR数をPBIの成果にしない。

### 推奨する構成

```markdown
[利用者]として、[実現したいこと]ができるようにしたい。
なぜなら、[その理由・価値]だからだ。

## Why

現状：[確認できた現状]
影響：[利用者・運用・品質への影響]
目指す状態：[改善後に観察できる変化]

## ユーザーに提供する体験

- [利用者ができるようになること]

## 受け入れ条件

- [第三者が満たしたか判断できる条件]

## 対象外・制約

- [今回扱わないこと／守る必要がある制約]

## 関連

- Project: #166
- PBL: #167
- Related: #番号
```

冒頭のストーリーとWhyは短くする。Whyはストーリーを言い換えるだけでなく、現状と影響の根拠を補う。「ユーザーに提供する体験」は利用者が観察できる結果を書く。実装方法や関数名だけを成果として書かない。

### PBIの例（架空）

```markdown
NixOS の利用者として、インストールしていないアプリも識別しながら探したい。
なぜなら、導入前にアプリを比較し、安心して選びたいからだ。

## Why

現状、候補のアイコンがインストール済みパッケージのローカルファイルに依存すると、未インストール時に識別情報が不足する。利用者は一覧の中からアプリを見分けづらい。

## ユーザーに提供する体験

- アプリが未インストールでも、取得可能なメタデータからアイコンを表示できる。
- アイコンの取得に失敗しても、空白ではなく汎用アイコンで識別できる。
```

実際のIssueでは、確認できた証拠や現在のコードに合わせて書き換える。例を事実として転記しない。

## Task：必要な理由と完了条件を書く

TaskはPBIの成果へどう寄与するかが分かる範囲にする。PBIとの紐づけが確定していない段階でも、調査や作業は開始できる。目的の似たTaskが複数ある場合は、同じ成果に寄与するか確認してから統合する。関数・ファイルごとに機械的にIssueを分割しない。

```markdown
## Why

この作業が必要な理由と、現在の障害を記載する。

## 方針 / How（分かっている場合）

対象、候補、制約、関連実装などを簡潔に記載する。仮説は仮説と明記する。

## 作業完了条件

- 完了を判定できる結果を記載する。

## 検証

- 関連する自動テスト、手動確認、実機確認を記載する。未確認は未確認とする。

## 関連

- Project: #166
- PBL: #167
- PBI / Blocked by / Related: #番号
```

Howや技術選定が未定でも起票できる。調査して決めることが成果なら、決定事項・比較した候補・採用理由・残る不確実性を完了条件とする。

## Bug：症状と期待値を分ける

Bugは原因が分かっていなくても起票する。原因が未確定なのに「〇〇が原因」と断定しない。

```markdown
## 実際に起きていること

実際に確認した挙動と発生頻度を書く。

## 期待すること

利用者が期待する挙動を書く。

## 再現手順

1. ...
2. ...
3. ...

再現できない場合は、未確認と書く。

## 影響

利用者・設定・データ・性能・安全性への影響を書く。

## 環境・証拠

NixOS / Wayland compositor / GPU / WebKitGTK / 起動方法 / ログなど、原因の切り分けに必要な情報のみを書く。取得できていない情報は推測しない。

## 完了条件

- 再現条件で期待した挙動になる。
- 影響する境界条件と回帰テストを確認する。
```

## NXC特有の記述ルール

### 事実・仮説・決定を区別する

- **確認済み:** 実際に読んだコード、再現した操作、実行したコマンド、得られたログやテスト結果。
- **仮説:** 根拠はあるが未確認の原因や対応案。「可能性がある」「検証する」と書く。
- **決定:** 合意した仕様・制約。判断理由を必要な範囲で残す。

調査時点のブランチやコミットを記録するのは有用だが、実装が進んだら古い状態を現状として扱わない。過去の調査結果は「調査時点」と明記する。

### 安全性・設定変更を扱う場合

NixOS 設定、ファイル書き込み、権限、サービス変更、rollbackに関わるIssueでは、正常系だけでなく次も検討する。

- 想定外の構文・コメント・文字列・symlink・複数宣言などの境界条件
- 失敗時に部分更新や誤った成功判定が残らないこと
- 対象を安全に特定できない場合の動作（誤った対象にフォールバックしない）
- 既存設定・利用者データ・権限境界への影響

必要な安全性条件はIssue本文に残し、全テストケースや実行ログはPR・テストコード・CIへ置く。

### 性能を扱う場合

「高速化する」だけにせず、どの操作が遅いか、比較条件、悪化させない条件を記録する。測定していない値を目標値・改善実績として書かない。キャッシュ導入や再計算頻度の変更では、正確性・無効化条件も扱う。

### 調査・実装の詳細を残す範囲

再現手順、関連ファイル、具体的な受け入れ条件、重大な制約は有用なので省略しない。一方、同じ背景・手順・完了条件を複数節で重複させない。独立した複数の成果が混ざる場合はPBIとTaskへ分け、各Issueをリンクする。1つの成果を完了するために密接な技術手順であれば、1つのIssue内にまとめてもよい。

## Ready と Done

### Ready（作業を開始できる状態）

- 問題・目的と目指す結果を説明できる。
- 範囲と主要な制約が分かる。未確定項目は明示されている。
- 受け入れ条件または調査の成果物が判定できる。
- 重複Issue・依存Issue・関連PRを確認できる。

詳細なHowや全テストケースが未決定という理由だけで着手を止めない。

### Done（完了）

- 受け入れ条件を満たしている。
- 関連テストが追加・更新され、必要なFormat / Lint / Test / Build / CIが成功している。
- 安全性・データ保全に関わる変更は、失敗系・境界条件・復旧動作を確認している。
- 利用者向けの挙動や手順が変わった場合、ドキュメントを更新している。
- PRに確認した内容・未確認事項・残る制約を正直に記録している。
- 対応見送りは完了と混同せず、理由を残している。

Issueの受け入れ条件は「何ができれば成果か」、Doneは「変更を出荷できる品質か」を表す。詳細なテストケースの全件をIssueに埋め込まない。

## クローズ済みIssueと履歴

既存のクローズ済みIssueは開発履歴・判断の証跡として保持する。新ルール適用のためだけに本文を大量に書き換えない。誤情報の修正や後続作業への注意が必要な場合は、追記コメントまたは関連Issueから参照する。

PBLでは `completed`、`not planned`、`duplicate` などの終了理由を区別する。見送りや重複は実装完了として数えない。

## 起票後の流れ

1. Issue Form または空Issueで起票する。
2. 既存Issue・PR・コード・ログを確認し、事実と仮説を整える。
3. [PBL #167](https://github.com/Ni-gihub/nixos-json-controller/issues/167) にリンクし、優先度と依存関係を更新する。
4. 着手後に必要なHow・設計判断・受け入れ条件を追記する。
5. PRはWhy、変更内容、検証結果、未確認と残るリスクを説明し、関連Issueをリンクする。
6. 完了または見送りの理由に応じてIssueをクローズする。

Issueは問題・期待値・決定を共有するためのもの、PRは実装差分と検証の証拠を共有するためのものとする。
